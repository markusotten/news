### phase4-daas-200cap-false-positives — Citrix DaaS's What's New page has 800+ dated entries, so the 200-hash cache cap makes every entry beyond position 200 permanently show as "new"
- First seen: 2026-08-25
- Last seen: 2026-08-27
- Expected: Diffing 47 products' extracted entries against `.whatsnew-cache.json` should flag only genuinely new content.
- Actual: This run's extraction returned 841 raw entries for Citrix DaaS (page runs monthly release notes back to 2016 and none of it drops off). All other 46 products have far fewer entries than the 200 cap and were unaffected (0 spurious flags across all of them).
- Run did: did not report any of the 639 flagged hashes as new. Verified independently by scanning all 47 fetched pages' raw HTML for literal in-window date strings — none found on the DaaS page for this run's window either — so no genuinely new dated entry was missed. Reseeded `.whatsnew-cache.json` for all 47 products with this run's hashes (still capped at 200) so the top-of-page overlap check keeps working. **Recurred again on 2026-08-26 and 2026-08-27** with the same shape (top-200 hashes still match the prior cache: 200/200 overlap on 2026-08-27), confirming this is a stable, ongoing characteristic of the DaaS page rather than a one-off. Future runs on Citrix DaaS should keep relying on the top-200-overlap check (or an in-window date scan) rather than trusting a raw hash-diff, until the page's own history is capped or the cache is widened for this product specifically.

### phase4-cache-hash-scheme-unreproducible — this run's What's New extraction cannot be reconciled against `.whatsnew-cache.json`
- 2026-08-16 → 2026-08-17, recurred and fixed again 2026-08-21, recurred again 2026-08-22, recurred a final time and root-caused 2026-08-23 · reseeded `citrix/.whatsnew-cache.json` with a new, documented extraction method rather than chasing the unrecoverable 2026-08-14/2026-08-15 script (it was never committed, only its cache output was, so option (a) — locate and reuse it — was not viable).
- **2026-08-23 recurrence and fix:** re-implemented the method from its written description a fifth time and got the same symptom as 2026-08-22 — entry counts matched the 2026-08-22 cache exactly for most products (Citrix Analytics 39=39, StoreFront 58=58, Citrix Workspace app 69=69, Citrix Cloud 9=9 — the last is the identical example already logged in the 2026-08-22 paragraph below) but hash-set overlap stayed near-zero even on exact-count matches (117/1554 hashes overlapped across all 47 products), confirming this is not a one-off but a structural weakness in the skill: **the hash scheme was never actually reproducible from prose, because it depends on implementation details a written description can't fully pin down** (exact whitespace collapsing inside `first_line_of`, whether a trailing period is retained, Python `str.lower()` vs any Unicode-normalization step, sentence-boundary regex behavior on abbreviations, etc.) — five independent reimplementations by five different runs, all matching entry *counts*, have now failed to match hash *bytes*. Rather than attempt a sixth prose reimplementation, this run **committed the actual, working extraction code** to the repo as `citrix/whatsnew_extract.py` (the parser, style-detection and hashing functions) and `citrix/whatsnew_run.py` (the Phase 4 fetch-and-diff driver), so every future run imports the identical code instead of re-deriving it from this file's description. This should be the last recurrence of this defect — the standing method described below stays as documentation of what the committed code does, not as a spec to reimplement. As before, did **not** trust the hash-diff "new" flags from this reseed; cross-checked independently by scanning all 47 fetched pages' full HTML text for the literal in-window dates (`2026-08-22`, `2026-08-23`, `August 22, 2026`, `August 23, 2026`) — none were found on any of the 47 pages (unlike 2026-08-22, which found two page-footer banner matches). Reseeded `.whatsnew-cache.json` with this run's output (same method, all 47 products, capped at 200 hashes each). Net effect: no Phase 4 `Releases` entries were added to the 2026-08-23 daily note.
- **2026-08-22 recurrence:** re-implemented the 2026-08-21 method (narrative-vs-heading, most-headings-wins, single-entry fallback) from its written description again — the script still isn't committed, only described — and it reproduced the *shape* of the 2026-08-21 output well (product-by-product entry counts matched the 2026-08-21 cache exactly for 26 of 47 products, e.g. Citrix Analytics 39=39, StoreFront 58=58, Citrix Workspace app 69=69), but hash-set overlap against the 2026-08-21 cache was near-zero even on those exact-count matches (e.g. Citrix Cloud: 9=9 but 0 overlap; StoreFront: 58=58 but 15/58 overlap; XenCenter: 22=22 but 20/22 overlap) — confirming the mismatch this time is in hash *formatting* (whitespace/quote normalization or "first body line" truncation length), not heading-level selection as it was on 2026-08-21. Separately, found and fixed a real extraction bug: uberAgent's catalog What's New URL (`.../uberagent/current-release/whats-new.html`) redirects to `.../uberagent/8-x/whats-new.html`, a version-index stub listing "About uberAgent 8.1" / "About uberAgent 8.0" links rather than carrying real content — the single-entry fallback correctly detected this as thin but was extracting the stub's own one paragraph ("uberAgent 8.1 is the most recent update...") instead of the real release notes; fixed by following the stub's "About &lt;newest version&gt;" link to `.../8-x/whats-new/8-1`, which now extracts the true 4 entries (IGEL OS 12 app, Azure Monitor sunsetting, Splunk dashboard wording, Agent). Given the hash mismatch is now confirmed systemic rather than tied to one known-fixed root cause, reseeded `.whatsnew-cache.json` again with this run's output (same method, all 47 products) and did **not** trust any hash-diff "new" flags. Cross-checked independently instead: scanned all 47 fetched pages' full HTML text for the literal date window (2026-08-21T02:10:02Z–2026-08-22T02:09:11Z, i.e. `2026-08-21`/`2026-08-22`/`August 21, 2026`/`August 22, 2026` substrings anywhere in the page). Only two pages matched — Citrix DaaS and Citrix Virtual Apps and Desktops, both showing an `August 21, 2026` "last modified" page-footer banner (not a per-entry date) — and in both cases the page's top-listed narrative entries (Microsoft Entra single sign-on, Web sign-in (Preview), Connector Appliance latency, for DaaS) are the same items already on record from before this run (referenced in the 2026-08-16→2026-08-21 entry below as already known mid-August content), so the banner bump reads as a page-level edit rather than newly-shipped content, and neither was reported as new. No other product's page body contained an in-window date anywhere. Net effect: no Phase 4 `Releases` entries were added to the 2026-08-22 daily note.
- **2026-08-21 recurrence:** re-implementing the 2026-08-17 method from its written description (rather than from code, since the script itself was never committed) reproduced it closely enough to run, but diffing against the 2026-08-17 cache still flagged most products' entries as "new" — up to 100% mismatch on some (e.g. Citrix Cloud Government: 11 cached, 0 overlap). Root cause: the "finest heading level (h4, else h3, else h2) that occurs more than once" rule is ambiguous whenever a page uses more than one heading level for different structural roles — e.g. StoreFront uses `h2` for version numbers, `h3` for the ~58 real per-feature entries, and `h4` for exactly 3 headings inside one small Technical-Preview subsection; the finest-first rule locks onto that `h4` trio and misses the real content entirely. **Fix, now the standing rule:** compute candidate entries at all three levels and pick whichever level yields the *most* headings (still >1), not the finest one that merely clears the >1 bar. Also added a single-entry fallback (page `h1` + first `p` as one entry) for genuinely thin one-topic pages that have no repeated heading at any level and fewer than 3 narrative paragraphs — without it, such pages (Federated Authentication Service, Citrix DaaS Flex, HDX RealTime Optimization Pack, Citrix Secure Developer Spaces, Citrix VDA for macOS, NetScaler Console Service, NetScaler SDX) silently produced zero entries every run and could never be diffed. Reseeded the cache with this fixed method across all 47 fetchable products; the next run should diff cleanly against it. Because this run's diff was untrustworthy, did **not** report any hash-diff-derived "new" entries; instead cross-checked independently by (a) scanning every fetched page's own "last modified" banner date and any in-body "Release date:" text for the 2026-08-17T02:22:53Z–2026-08-21T02:10:02Z window, which flagged exactly 6 products (Citrix DaaS, deviceTRUST, Licensing, StoreFront, uberAgent, Citrix Workspace app), and (b) manually reading each flagged product's top-of-page content. All of it was already reported to the user in the non-skill ad-hoc root file `2026-08-19-Citrix-Product-Updates.md` (Citrix DaaS's Entra SSO/web sign-in/Connector Appliance items, deviceTRUST's five items, StoreFront's desktop-tile/power-actions items) except the Licensing entry (already covered by this run's own Phase 2 download of License Server 11.17.2 Build 56200) and uberAgent/Workspace-app-for-Mac 2607 (covered by this run's own Phase 2 downloads, enriched in the daily note with authoritative detail from their docs pages). Net effect: no Phase 4 `Releases` entries were added to today's note beyond enriching existing Phase 2 download entries, because everything genuinely new in-window was already surfaced elsewhere. NetScaler ADC/Console/Gateway's anchor pages continue to resolve to nav boilerplate with no real `h1`, so the single-entry fallback correctly declines to fabricate an entry for them.
- **Method (now the standing method for this skill):** fetch each fetchable product's What's New URL with `curl`. Parse with Python's stdlib `html.parser` into a lightweight tree, strip `script`/`style`/`nav`/`header`/`footer`/`aside`, then isolate the article body as the `<div class="sub-content-main">` block — present on every `docs.citrix.com`/`docs.xenserver.com` content page checked (confirmed on citrix-daas, citrix-cloud, storefront, workspace-app, secure-mail, enterprise-browser, xenserver/9); `docs.netscaler.com` landing pages have no such wrapper (they use styled `div`s instead of headings for their nav cards) so the whole `<body>` is used there instead, minus the same stripped tags. Within that region: if the page contains 3+ `<p>` elements whose first child is `<strong>` (excluding any nested inside `<li>`/`<td>`, and excluding inline callout labels — Note/Important/Benefits/Warning/Tip/Caution/Prerequisites/Requirements/Limitations/Example(s)) — the "monthly narrative" style used by citrix-daas, citrix-cloud, citrix-secure-mail, etc. — each such paragraph is one entry (title = the `<strong>` text, first body line = the rest of that paragraph). Otherwise, fall back to heading-based entries at the finest heading level (h4, else h3, else h2) that occurs more than once — the "one heading per version/topic" style used by citrix-workspace-app, storefront, citrix-enterprise-browser, xenserver — excluding a small denylist of purely structural section labels (New and enhanced features / Fixed issues / Known issues / Removed features / Deprecated features / Requirement / Removed). Hash = first 12 hex chars of `md5(lowercased "title|first body line")`. Cache keeps the 200 most recent hashes per product (page order is newest-first on every page checked).
- Ran this against all 47 fetchable products (46 from the prior run's catalog, plus the newly-added XenServer SDK — which is `none`, so not fetched). All 47 returned HTTP 200 and produced plausible per-entry titles (spot-checked citrix-daas, citrix-workspace-app, xenserver-9). Citrix DaaS's raw count is genuinely large (838 before the 200-cap) because its page runs monthly release notes back to 2016; a handful of nested-list sub-bullets (e.g. a "Protocol:" / "Frames Per Second:" pair inside one entry's own body table) still slip through as extra low-signal entries — a known, accepted imprecision, not a crash or a mass-miscount like the prior run's 1606/574.
- Per the skill's seeding rule, **reported nothing as new** from this reseed pass for any of the 47 products. Independently — not relying on the hash scheme at all — scanned every fetched page's plain text for exact day-level dates (`YYYY-MM-DD` and `Month D, YYYY`) inside the 2026-08-16T02:30Z–2026-08-17T02:11Z window; none were found on any of the 47 pages, so this reseed did not silently drop a same-day dated entry.
- **Consequence for readers:** Phase 4 coverage for 2026-08-16 (the prior run, which also reported nothing pending this fix) and this reseed pass on 2026-08-17 should both be read as "no diff available" for What's New content, not "confirmed nothing changed." Diffing resumes cleanly from the 2026-08-18 run onward, now against a same-method baseline.
