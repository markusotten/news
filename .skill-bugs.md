### catalog-missing-whatsnew-column — `citrix-produts.md` lacks the dedicated What's New URL column the skill requires
- First seen: 2026-08-13
- Last seen: 2026-08-14
- Expected: Per the skill, `citrix-produts.md` should hold "both the docs URL and the product's 'what's new' / release-notes URL" as two columns, so Phase 4 never has to rediscover the release-notes URL for a product.
- Actual: The file still has only a single `Docs URL` column. This run built a resolver script (curl + landing-page link scan, falling back to guessed suffixes) and achieved full 62/62 coverage for the first time — the resolved URLs are recorded here so a future run can populate the column without redoing the discovery work: most `docs.citrix.com` products use `<docs-url>/whats-new.html` or `<docs-url>#whats-new`; several (`Citrix Provisioning`, `Federated Authentication Service`, `Licensing`, `Linux Virtual Delivery Agent`, `Profile Management`, `Self Service Password Reset`, `Session Recording`, `StoreFront`, `Workspace Environment Management`, `deviceTRUST`, `HDX RealTime Optimization Pack`) use `<docs-url>/current-release/whats-new.html`; the five NetScaler products (`NetScaler (ADC)`, `NetScaler Console`, `NetScaler Console Service`, `NetScaler Gateway`, `NetScaler SDX`) and `LAS for NetScaler` resolve to a `#whats-new` anchor on the landing page rather than a distinct release-notes page — their actual version history lives in versioned `.../current-release/*-release-notes.html` pages already covered by Phase 2's download feeds, so the anchor page is thin. `Citrix App Layering`, `Session Recording Service`, `Citrix Secure Private Access`, and `Unicon eLux Scout` resolved to pages that are not really "what's new" content (a numbered doc-set page, a service-overview redirect, a legacy archive page, and a versioned release folder respectively) and need a manually-verified URL rather than the auto-resolved one. `Citrix Adaptive Authentication Service` and `Citrix Experience Insights Flex` genuinely have no dedicated what's-new page — record `none`.
- Run did: used the resolved URLs (falling back to the auto-discovery script) to check all 62 products for the window; found no entries dated inside it. The table itself was not restructured this run — that + hand-verifying the four questionable URLs above is still future work. **2026-08-14 addition:** `/whats-new.html` and `/current-release/whats-new.html` both 404 for 12 products not covered by the 2026-08-13 rule list: `Citrix Cloud Japan`, `Citrix DaaS Flex`, `Device Posture`, `Citrix Gateway Service`, `MAM SDK`, `Mobile Productivity Apps`, `Citrix Ready Workspace Hub`, `Citrix Secure Access`, `Citrix Secure Developer Spaces`, `uberAgent`, `Workspace Environment Management Service`, `XenCenter`. Of these, `XenCenter` and `uberAgent` resolve at `<docs-url>/current-release/whats-new.html` after all (transient 404 on first try, or the rule-2 list above is incomplete). `Citrix Cloud Japan`, `Citrix DaaS Flex`, `Device Posture`, `Citrix Secure Developer Spaces`, and `Workspace Environment Management Service` have no distinct whats-new page but their landing page contains a "What's new" section (unanchored or anchored) — treat as `<docs-url>#whats-new`. `Citrix Secure Access`, `Citrix Secure Developer Spaces`'s sibling `MAM SDK`, `Citrix Ready Workspace Hub`, `Citrix Gateway Service`, and `Mobile Productivity Apps` show no "what's new" content anywhere reachable and need hand verification — treat as `unverified:` for now, not `none`, since a hidden/differently-structured page can't be ruled out from a single fetch.

### whatsnew-cache-never-created — `.whatsnew-cache.json` does not exist despite skill requiring it
- First seen: 2026-08-14
- Last seen: 2026-08-14
- Expected: Phase 4 keeps `citrix/.whatsnew-cache.json` mapping product → entry hashes so undated what's-new entries can be diffed run over run.
- Actual: The file has never been created in this repo (no path, no git history). Prior runs that reported dated what's-new entries (e.g. the 2026-08-12 CVAD entries) worked only because those particular entries happened to carry dates inside the window — an undated new entry on any page would have been silently missed by every run so far.
- Run did: fetched all 61 non-skipped catalog what's-new pages and scanned for date strings matching the window instead of hash-diffing (no baseline exists to diff against). No in-window dated entries found. Did not create the cache file this run — building it requires a per-page entry-parsing pass that couldn't be completed alongside the other phases in this run; deferred to a future run so it doesn't further widen the gap on top of an already-large fix.
