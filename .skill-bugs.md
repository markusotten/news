### phase2-feed-pubdate-crosses-prior-window — a download-feed item can carry a pubDate later in the same UTC day than the run that already reported it
- First seen: 2026-09-04
- Expected: An item reported in one day's `Releases` section is never re-emitted by a later run, since the later run's window starts at the prior run's `last_successful_run`.
- Actual: The 2026-09-03 run reported "Citrix Virtual Delivery Agent for macOS 2607" (`.../components/mac-vda-2607.html`) dated 2026-09-03, using `last_successful_run` 2026-09-03T02:18:24Z as this run's window start. Re-fetching `citrix-virtual-apps-and-desktops.rss` this run found the identical item (same title, same link) with `pubDate` `Thu, 03 Sep 2026 12:00:00 -0400` = 2026-09-03T16:00:00Z — itself later in the same calendar day than both the 2026-09-03 run's recorded window end (02:07:55Z) and this run's window start (02:18:24Z). Per the skill's own inclusion rule ("stop reading once pubDate falls before the window", i.e. only a lower bound against `last_successful_run`), the item legitimately qualifies again this run, because this run's window start is still earlier in the day than the item's pubDate.
- Run did: excluded it from the 2026-09-04 daily note to avoid emitting the same release twice across daily notes, since it was already visible in the committed 2026-09-03 note. The underlying cause looks like Citrix's feed generator stamping `pubDate` at a fixed time-of-day (noon Eastern) for a same-day item regardless of true publish instant, which can place it after a same-day run's own window-close timestamp; a same-day boundary case like this could recur whenever `last_successful_run` and an item's `pubDate` fall on the same calendar day either side of the actual fetch. Suggested fix for a future run: when a Phase 2 item's link exactly matches a link already present in the immediately preceding daily note, treat it as already reported regardless of pubDate, rather than relying on the window-start comparison alone.

- **2026-08-21 recurrence:** re-implementing the 2026-08-17 method from its written description (rather than from code, since the script itself was never committed) reproduced it closely enough to run, but diffing against the 2026-08-17 cache still flagged most products' entries as "new" — up to 100% mismatch on some (e.g. Citrix Cloud Government: 11 cached, 0 overlap). NetScaler ADC/Console/Gateway's anchor pages continue to resolve to nav boilerplate with no real `h1`, so the single-entry fallback correctly declines to fabricate an entry for them.
- **Method (now the standing method for this skill):** fetch each fetchable product's What's New URL with `curl`. Parse with Python's stdlib `html.parser` into a lightweight tree, strip `script`/`style`/`nav`/`header`/`footer`/`aside`, then isolate the article body as the `<div class="sub-content-main">` block — present on every `docs.citrix.com`/`docs.xenserver.com` content page checked (confirmed on citrix-daas, citrix-cloud, storefront, workspace-app, secure-mail, enterprise-browser, xenserver/9); `docs.netscaler.com` landing pages have no such wrapper (they use styled `div`s instead of headings for their nav cards) so the whole `<body>` is used there instead, minus the same stripped tags. Within that region: if the page contains 3+ `<p>` elements whose first child is `<strong>` (excluding any nested inside `<li>`/`<td>`, and excluding inline callout labels — Note/Important/Benefits/Warning/Tip/Caution/Prerequisites/Requirements/Limitations/Example(s)) — the "monthly narrative" style used by citrix-daas, citrix-cloud, citrix-secure-mail, etc. — each such paragraph is one entry (title = the `<strong>` text, first body line = the rest of that paragraph). Otherwise, fall back to heading-based entries at the finest heading level (h4, else h3, else h2) that occurs more than once — the "one heading per version/topic" style used by citrix-workspace-app, storefront, citrix-enterprise-browser, xenserver — excluding a small denylist of purely structural section labels (New and enhanced features / Fixed issues / Known issues / Removed features / Deprecated features / Requirement / Removed). Hash = first 12 hex chars of `md5(lowercased "title|first body line")`. Cache keeps the 200 most recent hashes per product (page order is newest-first on every page checked).

- Per the skill's seeding rule, **reported nothing as new** from this reseed pass for any of the 47 products. Independently — not relying on the hash scheme at all — scanned every fetched page's plain text for exact day-level dates (`YYYY-MM-DD` and `Month D, YYYY`) inside the 2026-08-16T02:30Z–2026-08-17T02:11Z window; none were found on any of the 47 pages, so this reseed did not silently drop a same-day dated entry.
- **Consequence for readers:** Phase 4 coverage for 2026-08-16 (the prior run, which also reported nothing pending this fix) and this reseed pass on 2026-08-17 should both be read as "no diff available" for What's New content, not "confirmed nothing changed."
