### citrix-blog-url-migration-false-recency — citrix.com/blogs URL scheme lost the day-of-month, and the migration itself makes every page look freshly modified
- First seen: 2026-09-17
- Expected: A blog post's URL path (`/blogs/YYYY/MM/DD/slug/`), the page's `published-time` meta tag, and `lastModified` in `https://www.citrix.com/query-index.json` all reflect the post's true editorial publish date, per the skill's own guidance ("Citrix blog URLs embed the publish date... trust that over relative labels").
- Actual: Sometime on 2026-09-16, `www.citrix.com/blogs/` was migrated to a new URL scheme that drops the day-of-month (`/blogs/YYYY-MM/slug`, e.g. `/blogs/2026-09/citrix-acquires-numecent`); the old dated URLs from prior daily notes still resolve, but only via a 301 redirect (`location: /blogs/2026-09/<slug>`, confirmed via `curl -D -`) to the new form. As part of that migration, **every** blog page on the site — including ones from 2024 and 2025 — got its `published-time` meta tag and its `query-index.json` `lastModified` value bumped to 2026-09-16, all clustered within ~2 seconds (1789583779–1789583781), i.e. a bulk re-publish/reindex event, not real edits. Naively trusting either of those two signals for "what's new" would have wrongly surfaced roughly 3,237 pages (the site's entire `query-index.json` row count) as freshly published today. The true editorial date survives only in the page body: an inline author byline (`<author-name> <ISO-8601 timestamp>`, e.g. "Sridhar Mullapudi 2026-09-01T08:00:28.000Z") on blog posts, and a `"Date":"..."` field embedded in a script block on `/news/announcements/` press pages.
- Run did: for Phase 5, ignored `published-time`/`lastModified` entirely and instead filtered `query-index.json` to the current month's `/blogs/2026-09/` folder (only 6 posts total this run) and read each one's true byline date directly from its body. All 6 turned out to predate this run's window (2 already reported in the 2026-09-16 daily note, the other 4 dated 2026-09-01/09-02/09-14/09-14) — the same body-byline check found the two `/news/announcements/sep-2026/` press items also predate the window (`"Date":"2026-09-01T08:00:00..."` for the Numecent announcement) despite no `published-time` meta at all on that template. No Press entries were reported this run. Future runs: keep reading the body byline/`"Date"` field rather than page metadata for both `/blogs/` and `/news/announcements/`; consider using each site's underlying JSON (`query-index.json` filtered by path prefix; the WordPress-based `netscaler.com`/`xenserver.com` blogs already expose a reliable `/wp-json/wp/v2/posts?orderby=date` endpoint that sidesteps this problem entirely).

### phase2-feed-pubdate-crosses-prior-window — a download-feed item can carry a pubDate later in the same UTC day than the run that already reported it
- First seen: 2026-09-04
- Expected: An item reported in one day's `Releases` section is never re-emitted by a later run, since the later run's window starts at the prior run's `last_successful_run`.
- Actual: The 2026-09-03 run reported "Citrix Virtual Delivery Agent for macOS 2607" (`.../components/mac-vda-2607.html`) dated 2026-09-03, using `last_successful_run` 2026-09-03T02:18:24Z as this run's window start. Re-fetching `citrix-virtual-apps-and-desktops.rss` this run found the identical item (same title, same link) with `pubDate` `Thu, 03 Sep 2026 12:00:00 -0400` = 2026-09-03T16:00:00Z — itself later in the same calendar day than both the 2026-09-03 run's recorded window end (02:07:55Z) and this run's window start (02:18:24Z). Per the skill's own inclusion rule ("stop reading once pubDate falls before the window", i.e. only a lower bound against `last_successful_run`), the item legitimately qualifies again this run, because this run's window start is still earlier in the day than the item's pubDate.
- Run did: excluded it from the 2026-09-04 daily note to avoid emitting the same release twice across daily notes, since it was already visible in the committed 2026-09-03 note. The underlying cause looks like Citrix's feed generator stamping `pubDate` at a fixed time-of-day (noon Eastern) for a same-day item regardless of true publish instant, which can place it after a same-day run's own window-close timestamp; a same-day boundary case like this could recur whenever `last_successful_run` and an item's `pubDate` fall on the same calendar day either side of the actual fetch. Suggested fix for a future run: when a Phase 2 item's link exactly matches a link already present in the immediately preceding daily note, treat it as already reported regardless of pubDate, rather than relying on the window-start comparison alone.
